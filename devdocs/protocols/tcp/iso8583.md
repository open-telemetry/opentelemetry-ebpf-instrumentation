# ISO 8583 over TCP

OBI recognizes ISO 8583 exchanges on any TCP port, including asynchronous responses that arrive without a captured request. A financial response with message type indicator (MTI) `0210` produces a span named `ISO 8583 0200`. The endpoint receiving the response reports a client span. The endpoint sending it reports a server span.

## Response time

When the response echoes the original transmission date and time in data element 7 (DE7), OBI subtracts that timestamp from the socket observation time. This estimates the time since the originator sent the message, including time spent before OBI saw it. DE7 has whole-second precision, so the estimate can include up to one extra second. It also depends on the originator and observer clocks being synchronized. The `duration.source` attribute is `field_7`.

OBI checks the entire `MMDDhhmmss` value and accepts transmission times up to two minutes before the observation. The default switch timezone is UTC. For a switch using New York time, set the v2 option `capture.instrumentation.iso8583.transmission_timezone` to `America/New_York`. The date check handles midnight and New Year and rejects a stale timestamp with the same minute and second.

If DE7 is absent, invalid, or outside that window, OBI can measure the elapsed time between the request and reply at the socket. The duration source is `capture`. On a multiplexed connection, the reply must echo the systems trace audit number (DE11) and have a compatible MTI. For example, if a terminal sends two `0100` authorizations before receiving either `0110`, OBI uses each reply's DE11 to find its request even when the second authorization completes first. A single captured exchange can omit DE11. When both messages declare DE7, the values must also match for capture timing.

OBI retains up to 128 outstanding requests per connection across 1,024 process and connection pairs. Requests are eligible for matching for two minutes. If several outstanding requests match the same reply, or its request was never captured, the reply needs a usable DE7 to produce a duration. A switch that replaces DE7 with its own send time changes what that estimate measures.

## Wire formats

Each message starts with either a two-byte big-endian length or four ASCII decimal length digits. The length counts the bytes after the prefix. OBI accepts two message encodings.

| MTI | Bitmap |
| --- | --- |
| Four ASCII digits | 16 hexadecimal characters per bitmap |
| Two packed-BCD bytes | Eight binary bytes per bitmap |

The MTI must immediately follow the length. OBI checks the version, message class, function, origin, and primary and optional secondary bitmaps. Responses to a repeat can use the original origin digit.

To locate the timing fields, OBI supports a two-digit length and up to 19 digits for the account number (DE2). In the supported packagers, DE3 and DE11 have six digits, DE4–DE6 have twelve, DE7 has ten, and DE8–DE10 have eight. Each numeric field uses ASCII digits or packed BCD according to the message encoding. [jPOS packagers](https://jpos.org/docs/tutorial/iso-packager/generic-packager/)

The parser walks up to 32 length-prefixed messages per captured direction. Batched responses share that buffer's observation time. The frame lengths must account for the observed bytes. A standalone reply can exceed the inline capture limit when its header and timing fields fit and its declared length accounts for the whole read or write. A split frame or a batch with an uncaptured frame header can prevent detection. TPDU or proprietary headers, mixed field encodings, and unframed streams are outside this detector's coverage.

For unclassified TCP exchanges, OBI tries ISO 8583 after the other protocol detectors and requires the same framing and encoding in both directions. A plausible ISO 8583 prefix enables per-operation capture for that TCP record. The multiplexed TCP reader provides the byte ranges and observation times of captured writes. If another reply arrives after the record was emitted, the reader routes the new bytes and timestamp to the decoder that recognized the exchange.

OBI uses the normal TCP capture limits. It can track up to 33 socket operations in the initial direction per record, across 1,024 records. If a request's header or DE11 falls outside the captured bytes, its reply needs DE7 for timing. Increase `ebpf.buffer_sizes.tcp` (`OTEL_EBPF_BPF_BUFFER_SIZE_TCP`) to capture longer exchanges.

## Telemetry and configuration

The instrumentation selector is `iso8583`. Default traces and application RED metrics include it. In config v2, `capture.instrumentation.iso8583.enabled.traces` and `metrics` control the telemetry signals independently.

| Signal | Data |
| --- | --- |
| Client or server span | `network.protocol.name=iso8583`, initiating MTI in `mti`, duration source, connection endpoints, and transaction references (`stan` and `rrn`) when captured |
| `iso8583.request.duration` | Response time in seconds, grouped by MTI, duration source, endpoint role (`request.type`), and authorization outcome (`auth.outcome`) by default |
| Metrics histogram | `iso8583_request_duration_seconds` |

The metrics expose the role as `request_type`. OBI reports separate `client` and `server` series when it observes both endpoints. The TCP tracker identifies each socket by PID and endpoint pair, so a process that owns both ends of a loopback connection can merge the two observations.

### Authorization outcomes

OBI reads DE39 on replies to authorization and financial requests, such as `0110` and `0210`. The metric attribute is `auth.outcome` in OTLP and `auth_outcome` in Prometheus.

| Outcome | Meaning | Example 1987 / 1993 codes |
| --- | --- | --- |
| `approved` | Full approval | `00` / `000` |
| `partially_approved` | Part of the amount approved | `10` / `002` |
| `declined` | Business decline, such as insufficient funds | `51` / `116` |
| `technical_error` | Processing or routing failure, such as issuer unavailable | `91` / `907` |
| `unknown` | Missing, truncated, unsupported, or unrecognized DE39 | |
| `not_applicable` | Advice acknowledgment, reversal, network management, or another message outside the decision flow | |

The decoder follows the jPOS 1987 and 1993 ASCII and binary field layouts. DE39 is two text bytes in the 1987 layouts. In the 1993 layouts it is three ASCII digits or three packed digits with a trailing zero nibble. A processor can use different field widths or assign its own response codes under the same MTI. OBI maps common codes and reports `unknown` for 2003 authorization and financial decisions. [jPOS packagers](https://jpos.org/docs/tutorial/iso-packager/generic-packager/), [Worldpay response codes](https://docs.worldpay.com/access/products/reference/refusal-response/scheme-codes), [Nexi action codes](https://developer.nexigroup.com/softposmobilepos/en-EU/docs/action-code/)

The inline TCP buffer captures up to 128 bytes of a paired reply and 256 bytes of the first standalone reply. Later replies use the available append capture. A timed response whose DE39 falls beyond the captured bytes still contributes to the histogram with `auth.outcome=unknown`.

Client and server spans include the six-digit systems trace audit number (`stan`, DE11) and the retrieval reference number (`rrn`, DE37) by default when captured. OBI reads DE37 in the 1987 and 1993 layouts. For each identifier, OBI uses the reply value when available and otherwise uses the matched request. Both attributes are strings and preserve leading zeroes. OBI strips trailing space padding from DE37. The duration histogram excludes both identifiers.

The four-digit MTI preserves leading zeroes. The timestamps, account numbers, amounts, and raw response codes are omitted from these signals.
